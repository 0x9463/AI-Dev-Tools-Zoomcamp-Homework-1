# Development process

- GitHub Issues are the canonical active backlog; [backlog.md](backlog.md) is an index of links.
- Use the [Orchestrator role](../team/orchestrator.md) for coordination only. Its workflow and handoff template require the role used, issue number, revision where applicable, result/status, evidence, and next role at each transition. Delegate PM, Engineer, and QA work to separate role agents, keeping QA independent of implementation.
- Work on one issue at a time. Read its current description and acceptance criteria before starting; confirm that its prerequisites exist.
- Read only the additional project documents relevant to the task, using the document map in [AGENTS.md](../AGENTS.md).
- When an issue requires product clarification, use the [Product Manager role](../team/pm.md) before implementation. The PM rewrites the GitHub issue itself using the [task-grooming template](task_grooming_template.md); the issue remains the canonical task. Resolve questions that affect expected behavior or acceptance criteria before implementation. The PM does not implement or test the feature.
- Use the [Software Engineer role](../team/software-engineer.md) to implement one groomed issue at a time according to its acceptance criteria and documented constraints, without changing the criteria. If a criterion is contradictory, impossible, or unclear after grooming, comment on the issue explaining the problem and stop the affected implementation until clarified.
- Do not silently expand scope. Raise missing requirements or additional work explicitly before including them in the current issue.
- Commit regularly after meaningful changes, keeping commits focused on the issue and excluding unrelated work.
- Run the tests and checks appropriate to the change and complete the issue's required workflow. Record validation results and any remaining limitations.
- The Engineer leaves the issue open, including after implementation and validation are complete, and adds an issue comment summarizing what was implemented or reused, tests/checks and results, commit reference(s), and any remaining limitation. Follow the role's definition of done before reporting completion.
- Implementation completion is a handoff to the [QA Engineer role](../team/qa-engineer.md), not issue completion. The Software Engineer must not perform the QA role on its own work. QA reads the current groomed issue and the Engineer's completion comment, inspects the implementation and relevant documentation, independently verifies every acceptance criterion and the issue's important edge cases through observable behavior, and runs existing tests and appropriate project checks. Add focused tests only when necessary to verify a criterion or expose a defect; do not silently change scope, acceptance criteria, or product requirements.
- QA adds a GitHub issue comment recording a binary **PASS** or **FAIL** verdict, every acceptance criterion checked, validation evidence, tests/checks executed and results, defects or limitations, and the commit/revision tested. **PASS** requires every criterion to be demonstrably satisfied, required tests/checks to pass, and no regression to be found; only then may the issue be considered complete and closed.
- If any criterion fails or cannot be verified, a required check fails or is blocked, or a regression is found, QA reports **FAIL**, documents exactly what failed and how to reproduce it (or the verification blocker), and leaves the issue open for the Software Engineer to correct. Unclear requirements return to grooming without QA changing them. After corrections, the Engineer posts an updated completion comment and hands the issue back for independent QA of the updated revision.
- The Orchestrator hands the exact Engineer-tested commit to QA. Each correction requires a new Engineer completion comment and revision, followed by independent QA. Repeat until PASS or a genuine blocker requires user intervention: an unresolved product decision, unmet prerequisites, an unavailable required external action, or repeated attempts exposing a blocker outside the issue scope. PASS makes only the reviewed revision and criteria eligible for completion; subsequent changes require a fresh Engineer → QA handoff. Completion actions remain subject to the user's authorized scope.
